# 国际化开发指南

WeKit 的界面资源以英语为源语言，并提供简体中文和繁体中文目录。语言状态按进程维护，
既不会修改微信的全局 `Configuration`，也不会在模块进程和微信进程之间同步 MMKV。

## 资源目录

| 目录 | 用途 |
|------|------|
| `app/src/main/res/values/strings.xml` | 英语源目录，也是缺少受支持翻译时的 fallback |
| `app/src/main/res/values-zh-rCN/strings.xml` | 简体中文目标目录 |
| `app/src/main/res/values-zh-rTW/strings.xml` | 繁体中文目标目录 |

用户可选择跟随系统、英语、简体中文或繁体中文。跟随系统时会解析系统的语言列表；没有
匹配到受支持语言时回退到英语。不要新增 `values-zh`、其他 `values-zh-*` 目录，或用地区
目录绕过现有三目录校验。

## 进程边界

WeKit 有两个资源环境：

- `LocaleResourceMode.ModuleApp`：独立模块应用自身的界面和资源。
- `LocaleResourceMode.InjectedHost`：注入微信进程、依赖模块资源注入的界面和资源。

`ModuleApplication` 运行在模块进程，而 WeKit 设置及其 MMKV 状态运行在微信进程。
因此模块进程中的 `WeKitLocaleController.initializeModuleProcess()` 只能跟随系统语言，
不能读取微信进程里的 `WePrefs`。微信完成 MMKV 初始化后，才由宿主进程调用
`initializeInjectedHost()` 读取和更新用户选择。

不要通过 IPC、广播、Provider 或轮询把两个进程的语言状态强行同步。测试微信内的 WeKit
设置页时，也不能用 `am start` 直接启动 `SettingsActivity`；它是寄生在微信进程里的界面，
必须通过微信内入口或现有 Activity 代理链路打开。独立模块应用只负责自己的界面和“打开
模块设置”等入口。

## Compose 界面

Compose 根节点应进入与所在进程匹配的 `WeKitLocaleProvider`。Provider 同时提供本地化的
`LocalContext` 和 `LocalConfiguration`，因此其子树可以正常使用 `stringResource`：

```kotlin
WeKitLocaleProvider(mode = LocaleResourceMode.InjectedHost) {
    Text(text = stringResource(R.string.example_title))
}
```

模块应用的 Compose 根节点使用 `LocaleResourceMode.ModuleApp`。如果现有主题或上层根节点
已经提供了正确模式，不要在普通子组件中重复包装 Provider。

Miuix `WindowDialog` 会创建独立 composition，普通父级的 CompositionLocal 不会自动传入。
微信宿主中的窗口对话框必须使用 `WeKitWindowDialog`，由它在窗口内容中重新进入
`InjectedHost` Provider：

```kotlin
WeKitWindowDialog(
    show = showDialog,
    title = stringResource(R.string.example_title),
    onDismissRequest = { showDialog = false },
) {
    Text(text = stringResource(R.string.example_message))
}
```

## 非 Compose 界面

Toast、原生对话框、通知、菜单和异步回调应在内容真正显示时创建本地化 Context：

```kotlin
val localizedContext = LocalizedContextFactory.create(
    base = context,
    locale = WeKitLocaleController.resolvedLocale,
    mode = LocaleResourceMode.InjectedHost,
)
showToast(localizedContext.getString(R.string.example_saved))
```

如果同一功能里多次使用，可以提供按领域命名的小型 helper，但 helper 必须在每次调用时读取
`WeKitLocaleController.resolvedLocale`。不要把已解析的 `String` 存进 `object`、单例、菜单
注册表、通知模板或长生命周期回调；否则用户运行时切换语言后仍会看到旧文本。跨异步边界时
传递资源 ID、格式参数或语义状态，在最终展示处解析字符串。

数字、日期和时间也要在使用时根据 `WeKitLocaleController.resolvedLocale.androidTag` 创建
`Locale` 后格式化，不能隐式使用 JVM 默认语言。

## 编写资源

### 命名与目录一致性

- 使用描述用途的 `snake_case` 名称，并保留已有功能或界面前缀。
- 中文目录可以暂时缺少源目录中的 key，此时 Android 会显示英语 fallback；中文目录不能
  出现英语源目录中不存在的 key。
- 目标条目必须与同名源条目保持 `string`、`plurals` 或 `string-array` 类型一致，并兼容
  其占位符和 markup 结构。
- 仅在默认目录中声明 `translatable="false"` 的技术资源，不要复制到目标语言目录。

功能注解、配置键、DexKit 匹配字符串、类名、协议字段、SQL、URL、日志和原始服务器内容是
技术数据，不应仅因为最终可能出现在文本中就翻译。面向用户的标题、说明、按钮、Toast、
对话框、菜单和无障碍文本应进入资源目录。

### 格式化占位符

使用带索引的 Java Formatter 占位符，例如：

```xml
<string name="example_progress">Processed %1$d of %2$d items</string>
```

目标语言必须保留相同的参数索引和转换类型。允许按语序调整参数位置，也可以保留宽度、精度
等格式修饰，但不能把 `%1$d` 改成 `%1$s`。字面量百分号使用 `%%`；不要让转义后的内容被
误当成真实占位符。

### 复数

数量相关文本使用 `plurals`，并把数量同时作为选择参数和格式参数传入：

```kotlin
localizedContext.resources.getQuantityString(
    R.plurals.example_item_count,
    count,
    count,
)
```

不同语言可以使用不同 quantity 类别，但每个目录必须满足 Android 资源结构和仓库校验器的
要求。

## 校验

修改任一资源目录后，至少运行：

```bash
cargo test -p xtask i18n_check
./x i18n-check
git diff --check
```

`./x i18n-check` 会校验允许的语言目录、XML、重复项、仅目标语言存在的资源、资源类型、
数组/复数结构，以及格式化占位符。它允许中文目录暂缺源 key，因为 Android 会回退到英语；
它也不能证明 Android 代码和宿主运行时行为正确。

改动 Kotlin、资源引用或 Compose 集成时，还要通过完整构建，确保 Rust native 库与 APK
一起刷新：

```bash
./x build
```

不要只运行 Gradle `assemble*`，它会复用 `jniLibs` 中已有的 native 库。

## 真机检查

桌面校验不能替代微信宿主中的手动测试。涉及语言或界面资源的修改至少应检查：

1. 在微信内打开 WeKit 设置，将语言依次切换为英语、简体中文、繁体中文和跟随系统。
2. 不重启进程，确认设置页、普通对话框、独立窗口对话框、面板和浮层立即刷新。
3. 触发非 Compose 菜单、Toast、通知和异步结果，确认没有缓存旧语言。
4. 切换系统语言后重新选择“跟随系统”，确认受支持语言正确映射，其他语言回退到英语。
5. 单独打开模块应用，确认它使用模块进程自己的系统语言状态且不会因访问宿主 MMKV 崩溃。
