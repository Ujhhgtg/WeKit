# 国际化开发指南

WeKit 的界面资源以英语为源语言，并提供简体中文和繁体中文目录。语言状态只存在于注入微信
进程的 payload 中，不会修改微信的全局 `Configuration`。

## 资源目录

| 目录 | 用途 |
|------|------|
| `app/src/main/res/values/strings.xml` | 英语源目录，也是缺少受支持翻译时的 fallback |
| `app/src/main/res/values-zh-rCN/strings.xml` | 简体中文目标目录 |
| `app/src/main/res/values-zh-rTW/strings.xml` | 繁体中文目标目录 |

用户可选择跟随系统、英语、简体中文、喵体中文或繁体中文。跟随系统时会解析系统的语言列表；没有
匹配到受支持语言时回退到英语。不要新增 `values-zh`、其他 `values-zh-*` 目录，或用地区
目录绕过现有三目录校验。

喵体中文是逻辑语言选项，共用 `zh-CN` 资源环境，不新增独立 Android 资源目录。

## 进程边界

`:app` 是 payload，只由 `:bootstrap` 加载进微信进程运行，不存在独立的模块应用进程。因此
WeKit 只有一种资源环境：注入微信进程、依赖 payload 资源注入的界面和资源。微信进程完成
存储初始化后，由 `LocaleController.initialize()` 读取和更新用户选择；语言状态保存在微信
进程的 `KvStore`（Room）中。

测试微信内的 WeKit 设置页时，不能用 `am start` 直接启动 `SettingsActivity`；它是寄生在
微信进程里的界面，必须通过微信内入口或现有 Activity 代理链路打开。

## Compose 界面

Compose 根节点应进入 `LocaleProvider`。Provider 提供本地化的
`LocalResources`、`LocalConfiguration` 和严格的 `LocalLocalizedContext`，因此其
子树可以正常使用 `stringResource`、`pluralStringResource`、`colorResource` 和
`painterResource`：

```kotlin
LocaleProvider {
    Text(text = stringResource(R.string.example_title))
}
```

`LocalLocalizedContext` 只用于命令式读取 WeKit 资源，例如 `getString`、`getText` 和
`resources.getQuantityString`。不能用它获取 `Activity`、创建窗口、启动 Activity Result 或
SAF、获取系统服务，或构造第三方 UI；这些操作需要平台 Context。

`LocalContext` 始终是 Compose 宿主提供的平台 Context，WeKit 不会替换它或转发单独的
AndroidX owner。Activity、Activity Result、SAF、窗口、Toast 宿主、剪贴板、
`PackageManager`、Coil 和系统资源都使用 `LocalContext`；仅 Activity API 使用
`LocalActivity.current`。同一调用点同时需要平台能力和 WeKit 文本时，应显式读取两个 local。

如果现有主题或上层根节点已经提供了 `LocaleProvider`，不要在普通子组件中重复包装。

Miuix `WindowDialog` 会创建独立 composition，普通父级的 CompositionLocal 不会自动传入。
微信宿主中的窗口对话框必须使用 `WeKitWindowDialog`，由它在窗口内容中重新进入
`LocaleProvider`：

```kotlin
WeKitWindowDialog(
    show = showDialog,
    title = stringResource(R.string.example_title),
    onDismissRequest = { showDialog = false },
) {
    Text(text = stringResource(R.string.example_message))
}
```

`CommonContextWrapper` 只服务于 `showComposeDialog`、全屏面板等显式窗口入口，负责模块
资源/classloader 和宿主窗口服务转发。不要把它用于普通本地化资源读取；composition 外的
资源读取使用 `LocalizedResources.kt` 中的 `localizedString` / `localizedQuantity` helper。

## 非 Compose 界面

Toast、原生对话框、通知、菜单和异步回调统一通过 `i18n/LocalizedResources.kt` 中的 helper
读取 WeKit 资源。helper 在每次调用时重新解析 `LocaleController.resolvedLocale`，并注入
payload 资源：

```kotlin
// 不需要平台 Context 时使用顶层函数。
showToast(localizedString(R.string.example_saved))

// 同一调用点还需要平台 Context 时，使用 Context 扩展函数。
showToast(context, context.localizedString(R.string.example_saved, value))
val label = context.localizedQuantity(R.plurals.example_item_count, count, count)
```

- 字符串使用 `localizedString` / `Context.localizedString`，复数使用 `localizedQuantity` /
  `Context.localizedQuantity`。
- 不要新增按功能命名的 `localizedXxxString` 包装，也不要直接调用
  `LocalizedContextFactory.create`（`LocaleProvider` 是唯一例外）。
- 不要把已解析的 `String` 存进 `object`、单例、菜单注册表、通知模板或长生命周期回调；否则
  用户运行时切换语言后仍会看到旧文本。跨异步边界时传递资源 ID、格式参数或语义状态，在最终
  展示处解析字符串。

数字、日期和时间也要在使用时根据 `LocaleController.resolvedLocale.androidTag` 创建
`Locale` 后格式化，不能隐式使用 JVM 默认语言。

## 编写资源

### 命名与目录一致性

- 使用描述用途的 `snake_case` 名称，并保留已有功能或界面前缀。
- 中文目录可以暂时缺少源目录中的 key，此时 Android 会显示英语 fallback；中文目录不能
  出现英语源目录中不存在的 key。
- 目标条目必须与同名源条目保持 `string`、`plurals` 或 `string-array` 类型一致，并兼容
  其占位符和 markup 结构。
- 仅在默认目录中声明 `translatable="false"` 的技术资源，不要复制到目标语言目录。

功能注解、配置键、解析匹配字符串、类名、协议字段、SQL、URL、日志和原始服务器内容是
技术数据，不应仅因为最终可能出现在文本中就翻译。面向用户的标题、说明、按钮、Toast、
对话框、菜单和无障碍文本应进入资源目录。

### 格式化占位符

使用带索引的 Java Formatter 占位符，例如：

```xml
<string name="example_progress">Processed %1$d of %2$d items</string>
```

目标语言必须保留相同的参数索引和转换类型。允许按语序调整参数位置，也可以保留宽度、精度
等格式修饰，但不能把 `%1$d` 改成 `%1$s`。字面量百分号使用 `%%`；不要让转义后的内容被
误当成真实占位符。

### 复数

数量相关文本使用 `plurals`，并把数量同时作为选择参数和格式参数传入：

```kotlin
localizedContext.resources.getQuantityString(
    R.plurals.example_item_count,
    count,
    count,
)
```

不同语言可以使用不同 quantity 类别，但每个目录必须满足 Android 资源结构和仓库校验器的
要求。

## 校验

修改任一资源目录后，至少运行：

```bash
cargo test -p xtask i18n_check
./x i18n-check
git diff --check
```

`./x i18n-check` 会校验允许的语言目录、XML、重复项、仅目标语言存在的资源、资源类型、
数组/复数结构，以及格式化占位符。它允许中文目录暂缺源 key，因为 Android 会回退到英语；
它也不能证明 Android 代码和宿主运行时行为正确。

改动 Kotlin、资源引用或 Compose 集成时，还要通过完整构建，确保 Rust native 库与 APK
一起刷新：

```bash
./x payload build
```

不要只运行 Gradle `assemble*`，它会复用 `jniLibs` 中已有的 native 库。

## 真机检查

桌面校验不能替代微信宿主中的手动测试。涉及语言或界面资源的修改至少应检查：

1. 在微信内打开 WeKit 设置，将语言依次切换为英语、简体中文、繁体中文和跟随系统。
2. 不重启进程，确认设置页、普通对话框、独立窗口对话框、面板和浮层立即刷新。
3. 触发非 Compose 菜单、Toast、通知和异步结果，确认没有缓存旧语言。
4. 切换系统语言后重新选择“跟随系统”，确认受支持语言正确映射，其他语言回退到英语。
